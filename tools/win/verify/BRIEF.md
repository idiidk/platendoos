# Verifying Windows counterparts of rekordbox functions, hook sites and field offsets

Context: mods for rekordbox 7.2.19 (a JUCE DJ app) on macOS are being ported to the Windows build of the same version. The macOS build has symbols, the Windows exe (~/rbwin/x/rekordbox.exe, MSVC x64, image base 0x140000000) is stripped. A matcher paired functions; you verify, for our own mod project (interoperability).

## Tools (read-only)
- `python3 -I ~/rbwin/scripts/show.py <mac_symbol> [0x<win_addr>] [--max N]` (N=0: all): mac x86_64 disassembly (names; "[=win X]" = callee's current Windows match) then the Windows function's disassembly (calls annotated "= <mac name>" from the CURRENT matcher — usually right but can be wrong; imports imp:..; strings quoted).
- `python3 -I ~/rbwin/scripts/xref.py 0x<win_addr>` Windows callers/referrers; `xref.py --mac <symbol>` mac callers with their Windows matches.
- For raw Windows bytes at any address (leaf functions etc.): python with capstone + pefile (`pe.get_offset_from_rva(addr-0x140000000)`).
- Already verified, trust these: ~/rbwin/verify/core80.out.json, pilot.out.json (juce::String ctor/dtor/etc. — the real addresses).

## Compiler differences
clang/mac: args rdi,rsi,rdx,rcx,r8,r9, sret in rdi, `this` in rdi. MSVC/Windows: rcx,rdx,r8,r9 then stack; `this` in rcx; member function returning a class by value: hidden return pointer in rdx (after this); free function: in rcx. MSVC inlines more (tiny getters, String copy = lock inc at [ptr-0x10], CriticalSection enter/exit = imp:EnterCriticalSection/LeaveCriticalSection). Identical code is often folded into one function on Windows (e.g. String and Identifier destructors share code). Leaf functions (no stack frame) have no unwind info and may be missing from the tool's function list — read raw bytes.
Field offsets: usually equal on both, but shift when a class has std:: members before the field (MSVC std::string 32 bytes vs 24, std::function 64 vs 48, std::mutex 80 vs 64, std::shared_ptr 16 both, std::map 16 vs 24, std::vector 24 both) or different platform-specific members. Vtables: MSVC has one destructor slot (scalar deleting dtor, takes a flags arg) where mac has two (D1, D0); overloaded virtuals may be ordered differently; mac vtable entries start at +0x10 of the __ZTV symbol, Windows vtable entries at the vtable address.

## Items (input: your vN.json)
- kind "sym": mac symbol; `win` = current match or null; `cands` = candidates [addr, score, votes, sim]. Verdict: "ok" (win right), "wrong" (+ correct `win` if found), "pick" (unmatched: the right address, from cands or found otherwise), "inlined" (no separate Windows function: say where it's inlined, e.g. into which matched caller, and what it does there in one line), "absent", "unknown".
- kind "hook": a call site we patch: the `nth` (0-based) of `count` calls to `target` inside `caller` (mac symbols); hookkind -1 call, -2 tail call (jmp), n>=0: the address of target is taken into register xn (arm64 adr) — on Windows look for `lea reg,[rip+target]`. Find the Windows caller and the instruction that corresponds to the mac call. Report `sites` = ["0x<address of the call/jmp instruction>"] (exactly one when you're sure; the instruction must be E8 call rel32, E9 jmp rel32, or FF 15 call [rip+x]) and `target` = the Windows address it calls. If on Windows the target was inlined into the caller or the call is virtual (call [rax+..]), say so (verdict "inlined"/"virtual") with the details: then we hook differently.
- kind "offset": a field offset or constant the mod reads (`line` = its declaration with a comment saying what it is); `fn` is the mac function the recipe reads it from (arm64 instruction `recipe`, nth match), `mac_value` its mac value, `win_fn` the Windows match of fn if known. Find the same access in the Windows function (or another function using the same field) and report `value` = the Windows value (hex). For a "mov" recipe it's a constant, not a field.

## Output
Write incrementally (every few items) to ~/rbwin/verify/vN.out.json (same N): a JSON list of {"item": <sym / hook name / offset name>, "kind": "sym|hook|offset", "verdict": ..., "win": "0x...", "sites": [...], "target": "0x...", "fn": <offset fn>, "kind_recipe": <recipe>, "nth": <n>, "value": "0x...", "confidence": "high|medium|low", "why": "one line"} (only the fields that apply; for offsets copy fn/recipe/nth from the input as "fn", "kind_recipe", "nth"). High = you'd bet the app's stability on it. Don't spend more than ~6 minutes on an item: mark it unknown with what you found. Don't write anywhere else except scratch files under /private/tmp. Final reply: counts per verdict, plus anything surprising (systematic matcher errors).
